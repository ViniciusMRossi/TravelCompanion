# Lightweight Decisions

Record only decisions that materially affect maintainability or visible behavior.

- **D001 — One app module for V1.**
- **D002 — Firebase deferred from bootstrap.** Group sync already has an interface boundary.
- **D003 — Stable API 36 baseline.**
- **D004 — Runtime state never mutates packaged trip content.**
- **D005 — Real font binaries are added later; design typography remains locked.**
- **D006 — Lifecycle pinned to 2.10.0.** 2.11.0 requires compileSdk 37 / AGP 9.1.0 and cannot build on the API 36 baseline. See `docs/technical/DEPENDENCY-BASELINE.md`.
- **D007 — JDK 17 toolchain is auto-provisioned.** Foojay resolver in `settings.gradle.kts` keeps the pinned JDK 17 baseline working on machines that only have Android Studio's JDK 21.
- **D008 — The packaged trip is the sample Day 9 dataset.** `app/src/main/assets/trip/trip.json` is a copy of `trip-package/sample/sample-trip.json`; the minimal starter could not exercise screens 02 and 05. The approved `02 -> 05` flow opens **Baščaršija**, so that attraction, its audioguide and its rain Plan B were transcribed from the approved prototype into the sample package. Latin Bridge stays in the package as a second attraction that does *not* start the walk.
- **D009 — Trip length comes from the trip date window,** not from how many days are packaged, so "Dia 9 de 21" stays true while content for the other days is produced. The sample `endDate` was `2026-10-02`, a 20-day window that contradicted the approved "21 dias"; it is now `2026-10-03`. `validate_trip.py` checks every `dayNumber` against the window so this class of drift cannot return.
- **D010 — No image-loading library.** Packaged photography is decoded straight from assets; a missing binary falls back to the approved striped placeholder.
- **D011 — A walk names its starting attraction explicitly.** `walk.startAttractionId` was added to `trip.schema.json`. Sharing a `cityId` is not an association: every attraction in Sarajevo would otherwise claim the walk departs from it, and screen 05 would offer "Iniciar passeio" from the wrong place.
- **D012 — Duplicate critical items are merged, never de-duplicated.** The same item is routinely declared twice — curated on the day and in full on the transport that owns it. `distinctBy(id)` silently dropped "Ver ponto de embarque"; `CriticalItem.mergedWith` now unions the action links and keeps the first non-null of every field.
- **D013 — "Offline" is earned, not declared.** A document is only badged offline when `availableOffline` is true *and* `AssetResolver` finds the packaged file. Claiming offline access over a missing PDF is the one failure that only surfaces at a bus station.
- **D014 — `validate_trip.py` checks what JSON Schema cannot:** unresolved references, duplicate IDs, `dayNumber` against the trip window, and documents that promise offline access without a packaged file. Findings are warnings while `contentStatus` is prototype/draft and errors once it is `production`.
- **D015 — Playback is application-scoped.** `PlaybackController` lives on `AppContainer` and the player itself lives in a `MediaSessionService`. A screen-scoped player would stop the audioguide the moment the traveller navigates away or the phone rotates, which is exactly when the phone goes into a pocket.
- **D016 — A narrow `AudioEngine` seam sits between the controller and Media3.** It keeps ExoPlayer out of ViewModels and Composables, and it is what makes playback coordination testable without a device. It is deliberately limited to the operations the app performs.
- **D017 — Audio plays from `asset:///` URIs resolved by `AssetResolver`.** Bundled audio is read straight out of the APK and is never streamed; a guide whose file is absent reports `AudioNotPackaged` instead of failing in the decoder.
- **D018 — No notification permission prompt for the audioguide.** *(Corrected: an earlier revision requested POST_NOTIFICATIONS at the first tap.)* A `MediaSessionService` notification is exempt from the Android 13+ runtime permission, so the prompt bought nothing and interrupted the traveller before a single second of audio had played. The manifest declaration stays for the operational notifications of Phase 7, which do need it.
- **D019 — A documented prototype audio placeholder is packaged.** `trip/audio/attractions/bascarsija.prototype.wav` is synthesised by `tools/make_prototype_audio.py` (CC0, no third-party material: a short sine marker at each chapter start, silence in between) so the real playback flow can be exercised on a device. It runs the approved 720 s, so `ag.bascarsija` keeps `durationSeconds: 720` and screen 05 reads "Ouvir audioguia · 12 min" while the stated duration still matches the file on the device. It is labelled in the asset description and in `trip/audio/README.md`; only its chapter titles describe the placeholder rather than real narration.
- **D020 — Screen 05 keeps its approved action; playback surfaces in the compact player.** Screen 05 specifies one action ("Ouvir audioguia · N min") and screen 09 is the shared-player screen, so neither is reinterpreted. The design system's `TcAudioPlayer` compact variant — "the persistent bottom player … stays available while navigating" — lives in the shell above the bottom navigation. The full 52/68/52 transport is implemented in the same component and waits for screens 07/09.
- **D021 — An unplayable guide never disturbs playback.** A guide whose audio is not packaged is not offered at all (availability is known from content), and requesting one is a no-op: audio that is already playing keeps playing and the state keeps describing it. The UI and the engine can no longer disagree.
- **D022 — A finished guide replays from the start.** After `Ended`, both a fresh request and the play toggle seek to 0 and play, instead of resuming at the end where nothing would happen.
- **D023 — "Not playing" never overwrites a terminal state.** In Media3 `isPlaying = false` means paused, buffering, ended, failed, stopped *or* suppressed, and it can arrive before or after the state change that explains it. `Ended` and `Failed` therefore win over a bare pause signal, in either order, and a guide that ended is not given a resume point by the pause that follows it.
- **D024 — A lost connection drops its queue.** If `buildAsync` fails the pending commands are cleared; if the session disconnects, the player listener is removed and the controller is detached. Replaying a stale `prepare`/`play` after a later retry would resume the wrong guide; the next command reconnects from scratch instead.
- **D025 — Seek and chapter selection are deferred to their approved surfaces.** *(Closed: seek landed on screen 07 in D029, and the chapter list landed on screen 04 in D074. Neither capability was ever exposed anywhere else.)* Both are implemented and tested on `PlaybackController`, but the canonical screens put the −15/+15 transport on 07/09 and the chapter list on 04. Exposing them anywhere else would add a screen, which needs design review (`DESIGN-HANDOFF-v2.md` §10). **Approved decision: option (a)** — no solo player is created, and neither ±15 nor chapter selection is added to the compact player. Phase 2 ships play/pause as its reachable behaviour; the capabilities wait for Phases 3/4/6.
- **D026 — Schema 1.1: every local time names the zone it is written in.** `city`, `day` and both `transportEndpoint`s now require an IANA `timeZone`; a timeline item may override its day and otherwise inherits it. Package times are wall-clock, not instants: nothing records which zone that wall clock is in unless the field says so — harmless inside one zone, wrong the first time a leg crosses one. The `$defs/timeZone` pattern only rejects malformed names, so `validate_trip.py` resolves each name against the tz database (`tzdata` is now a declared dependency in `tools/requirements.txt`, since Windows ships none) and fails instead of passing when it cannot — always, not only once the package is `production`, since a wrong zone is a real defect at any content status. `tools/content_preflight.py` shares the same check via `validate_trip.known_timezones()`. An override equal to its own day is redundant but not reported as an error: it is valid per the schema and the package, and flagging it was never asked for. `walk.startAttractionId` (D011) and every other 1.0 field are unchanged.
- **D027 — `trip-package/production/` is versioned only by its `.gitkeep`.** The folder is part of the source → generated → review → production pipeline, so it has to exist in the repository; its contents are real travel documents, so none of them may. A directory-level ignore stops git descending and makes any negation inside unreachable, so the rule is `production/*` plus `!production/.gitkeep`. `source/private/` — the traveller's own bookings and identity documents, which are authoring *inputs* — is closed the same way by its own nested `.gitignore` (`*`, `!.gitignore`), kept local so the rule sits next to what it protects rather than being restated in the root file.
- **D028 — `trip-package/generated/` is versioned only by its `.gitkeep` too.** The review workspace was left open while `production/` was closed, but the difference is a stage in the pipeline, not a difference in what the files hold: `generated/trip.json` carries the booking locators, QR payloads and document references derived from `source/private/`, and `generated/research/` carries the material they came from (CONTENT-PACKAGE-SPEC.md §3, CONTENT-GENERATOR.md §2/§9). Data that D027 keeps out of the repository does not become publishable by sitting one directory earlier. The rule mirrors D027 exactly — `generated/*` plus `!generated/.gitkeep`, never a directory-level ignore — so the folder still exists for `tools/check_repo.py` and the pipeline still has its workspace. Human review therefore happens on the local files, which is where they were going to be reviewed anyway; nothing about the review step changes, only where it is understood to take place.
- **D029 — Screen 07 has its own transport; `TcAudioPlayerVariant.Full` is screen 09's.** The Phase 2 KDoc claimed `Full` served "screens 07 and 09", but the approved prototype and `TELAS-E-FUNCIONALIDADES-APPROVED.md` give them different treatments: screen 07 is an ink field with a white play button at 56 / 76 / 56dp on the bottom bar, screen 09 is a teal card at 52 / 68 / 52dp. `TcWalkTransport` implements 07's; the stale comment is corrected rather than the design bent to fit it. This is where D025 lands seek: `seekBy` was already implemented and unit-tested and now has its approved surface, and neither ±15 nor chapter selection is added anywhere else.
- **D030 — Walk Mode runs without location rather than not at all.** A foreground service of type `location` is refused outright by Android when the app holds no location permission, and the refusal is a `SecurityException` that takes the app down — observed on the device, not predicted. So the service starts only when the permission is actually held, and `WalkModeService` re-checks on its own in case the permission is revoked in between. The walk still runs: screen 07 says "Sem localização · histórias não aparecem sozinhas" and the audio is untouched, because location stories are enrichment. No walk notification is posted in that state, deliberately — the notification exists to satisfy Android's background-location rules, and with no location there is no background work to announce; audio, if any, already carries its own. The state is not only reachable by mistake: "Apenas esta vez" expires after the walk, and Android auto-revokes permissions for apps left unused for months, which is what a trip app is between trips. Screen 06's location row is therefore a way into the system settings page, since a second refusal makes the dialog stop appearing altogether.
- **D031 — Screen 07's story-arrival scaffold lives in `src/debug`, not behind a flag.** The approved prototype carries a dashed "Protótipo · simular chegada num ponto de história" control and notes it is not part of the product. It feeds the packaged story's own coordinates through the same `WalkModeController.onLocation` a GPS fix uses, so what it exercises is the real trigger decision rather than a bypass; without it, checking story triggering means standing in Baščaršija. It was first written in `main` behind `BuildConfig.DEBUG`, and reading the release DEX showed why that is not enough: both `simulateArrival` and the string "simular chegada" were present in the release binary, unreachable but shipped. A coordinate injector in a shipped artefact is a defect regardless of reachability, so the scaffold moved to `src/debug` with a null-returning counterpart in `src/release`, and the label moved with it. Verified again on the rebuilt release DEX: the prototype label is absent from every `classes*.dex`, and what remains of the name is the release source set's own `walkArrivalScaffold`, which returns null. The reproducible check is `grep -ac "Protótipo"` against the release DEX with the debug DEX as a positive control — not the pre-move symbol `simulateArrival`, which no longer exists under that name and so returns zero from any build, proving nothing.
- **D032 — The walk notification is cancelled on stop, not left to the service.** Stopping a foreground service removes the notification it owns, which is why `stopWalk()` originally only called `stopService`. But the walk notification is not always owned by a service: with no location permission none is started (D030), and the walk can still post progress. Ending such a walk left an `ONGOING|NO_CLEAR` notification for a walk that no longer existed, which the traveller cannot swipe away. `stopWalk()` now cancels the notification explicitly as well.
- **D033 — `ACCESS_BACKGROUND_LOCATION` is not declared until something uses it.** It was declared in the Phase 0 manifest and never exercised: Walk Mode holds location through a foreground service while a walk is running (D030), and passive background geofencing is not implemented. A sensitive permission that is declared but unused is friction in Play Store review and has to be justified in a form, while re-adding it in the phase that implements passive discovery costs one line. Removed now, on that basis. *(Re-declared on 2026-09-06 on exactly those terms: passive geofencing is implemented, this is the permission it needs, and nothing else in the app uses it — D103, D104.)*
- **D034 — Firebase is a dependency; `google-services.json` is not.** The SDK is on the classpath unconditionally, but the `com.google.gms.google-services` plugin is applied only when `app/google-services.json` exists — the plugin fails the build when the file is missing, which would make the repository unbuildable for anyone who has not been handed one (D002). Without configuration `FirebaseApp.initializeApp()` returns null, the repository reports `Disabled`, and everything else behaves identically; with the file dropped in, plugin and runtime both light up with no code change. The file stays out of the repository and out of these notes: no project ids, database URLs or keys are recorded anywhere versioned.
- **D035 — Sign-in is anonymous and invisible.** Database rules should be able to require `auth != null` rather than being open to anyone holding the URL, and the brief allows authentication the traveller never sees. Anonymous sign-in gives that: no account, no e-mail, no screen, nothing to enter — which keeps the "no login, no pairing, no code" invariant intact while the group's runtime state stops being world-writable. Failure to sign in makes the group unavailable, never an error local playback hears about.
- **D036 — Screen 09 renders packaged content, and stories still have no image.** The approved handoff for screen 09 specifies a hero photograph of the place, but schema 1.1 gives `story` no asset field and no link to the attraction that has one — `story.latin-bridge` and attraction `latin-bridge` correspond only by naming, which the package never promised. Resolving the hero by guessing `story.x` owns `img.x.hero` was written and then removed rather than shipped. Screen 09 therefore shows the striped placeholder captioned with the story's own name. The modelling fix is an `attractionId` on `story`, which drags a schema version, three package migrations and the guide with it — a content phase, not a screen detail. Recorded as not implemented rather than left to be discovered.
- **D037 — The group may move this phone, but never replace what it is playing.** *(Corrected: the screen that was said to own the decision did not act on it — see D042.)* `syncCorrection` can seek, pause or resume the local player to match the group. It never acts on a `Load` of its own accord: following one blindly would let the other participant swap the guide this traveller is listening to without them asking. The restraint is covered by a test. What the original wording described as already settled — "the screen that offers 'Ouvir juntos' owns that decision" — was only half written: nothing anywhere loaded the group's guide, so a phone with nothing playing could not join a shared listen at all. The owner is now real and is named in D042: arriving on screens 08/09 is the traveller's ask, it is spent once, and it can only ever load a guide onto a player that is holding none. A phone that is playing something is still never swapped, whoever asks.
- **D038 — The group is called reconnecting on this phone's own clock, not when Firebase says so.** *(Corrected: an earlier revision measured silence — see D039.)* Screen 09's amber note is how §3.3 reaches the traveller: the group failed, the audioguide did not. Relying on Firebase's own `.info/connected` to raise it does not work — with the radios off and screen 09 open, the SDK stayed silent for the full two minutes it was watched on the device while the screen went on reading "Sincronizado". So the controller keeps its own clock and its own threshold: twenty seconds without evidence that the group is reachable means reconnecting. Twenty is long enough that a hiccup does not flicker the screen and short enough that two people standing together are told while it still matters. What counts as evidence is D039. The check is a method the ticker calls, so it is driven by a clock in tests rather than by waiting.
- **D039 — Liveness is an acknowledged round trip, not the absence of silence.** D038 first read "nothing arrived for twenty seconds" as the group having gone away. On the device that turned out to be backwards: two people listening to the same guide write nothing for minutes at a time, so a perfectly healthy shared listen looks exactly like a dead one. Screen 09 was watched sitting idle and duly accused a reachable group of having failed after twenty quiet seconds — while edits made from outside the app were still landing on it within a second. Silence cannot be the signal in the other direction either, because Firebase raises events for this phone's own writes before they reach anyone, so an arriving snapshot is not proof that anything is listening. So the phone asks instead: `heartbeat()` refreshes this participant's `seenAt` every five seconds and reports only whether the *server acknowledged* the write, which a Realtime Database write does only once it has actually landed. Four unacknowledged beats — the same twenty seconds — turn the screen amber; one that lands turns it back. The beat doubles as this phone's presence refresh and as the tick that re-reads everyone else's, so liveness costs one small write and no extra traffic, and it only runs while screen 09 is open. Verified on the device in both directions: ninety idle seconds with the radios on left the screen clean, and thirty seconds with them off raised the amber note while the audio played through the outage without a gap. It has one consequence that had to be closed rather than accepted: making the group's snapshot arrive every few seconds puts every branch of `syncCorrection` on the same loop, and nothing publishes a stop when a guide simply ends — so a finished shared listen left the group node reading "playing" and asked each phone to resume a guide that was over, once per beat. A correction whose expected position is at or past the end of the loaded guide is therefore `None`. Found by reasoning about what the heartbeat changed and proved with a failing test, not on the device, which is why it is recorded here rather than among the device findings.
- **D040 — Screen 09 tells one truth about this phone, in both places it appears.** The traveller's own row read "Sincronizado" while the note directly under it read "Não foi possível sincronizar o grupo agora" — observed on the device, and both cannot be true. The original reasoning was that this phone knows its own playback without asking anyone, which holds only while it can still reach the group; when it is this phone that lost the server, it is not in step with anybody. Status and the traveller's own row therefore move together through one function, and nothing else moves with them: the other participants' rows are news only the group's snapshot can carry. Those rows are now real rather than assumed — each phone's `seenAt` is compared against server time, so someone who walked out of signal shows amber rather than being reported as keeping up until Firebase's own `onDisconnect` eventually removes them.
- **D041 — The three seconds of the countdown are not drift.** `startTogether` publishes the position playback is at *now* with an anchor three seconds out, and the audio does not stop while 3–2–1 is on screen. Until the anchor arrives, `expectedPosition` holds the group at its published position — correctly, since that is where playback *will* begin — so the gap between it and the local player widens by a second per second. The tolerance is two seconds, which means most of the countdown window is over it, and any snapshot arriving inside the window seeked the player backwards to the start position, mid-narration. The heartbeat guarantees snapshots inside that window. `syncCorrection` therefore answers `None` for any group whose agreed start moment has not arrived, for seeking and for resuming alike; a start nobody has reached yet moves nobody. Loading is decided before that gate on purpose — brief §5 says both devices preload before the moment arrives. Derived by reading the arithmetic rather than seen on the device, then reproduced by a failing test before it was fixed: three snapshots inside one countdown produced one `seekTo` that should not exist.
- **D042 — Arriving on screens 08/09 is the ask; it is the only thing that can load the group's guide.** The prototype has one way into a shared listen — the "Ouvir juntos" button under screen 07's transport — and it is the same button on both phones; the approved sheet for screen 08 calls it the transition between *asking* and "o áudio começar **nos dois aparelhos**", and brief §5 says both devices preload. So arriving here is this traveller's consent, and the controller decides what it means once the group answers: with nothing shared yet, propose a start (unchanged); with a listen already running on the guide this phone holds, follow it and publish nothing; with nothing playing here, take the group's guide at the group's position; with a *different* guide playing here, keep it. Three of those four were missing. The one that loads is a one-shot invitation spent inside `applyCorrection`, so the group still reaches the player through exactly one function and a phone that is playing something is never swapped (D037). Two consequences worth naming. First, publishing on every arrival was how the last person to open screen 09 dragged everyone else to their own position, as often as they liked — proposing is now only for when there is nothing to join. Second, two phones on different guides both read "Sincronizado", which is the failure with no symptom; screen 09 now says so on the row it is true about and in the note under the list, with the amber dot and the words "Ouvindo outra história" — *(Confirmed: approved. It is a fifth participant state, next to the four the boards draw, in their register and with no network vocabulary in it.)* It is reported only on the phone that is out of step: the group's payload carries one shared guide and no per-participant one, and widening it is a payload change this correction did not make.
- **D043 — The Phase 4 commit's trip prose is reverted; stories are written in the content phase.** `story.latin-bridge` was given a title, three paragraphs of specific historical claims, an asset description and a chapter title inside a commit about synchronization — with no `SOURCES.md`, no `FACT-CHECK.md`, and at least one claim (that Princip "havia desistido do plano naquela manhã") that is interpretation rather than established fact. `content/RESEARCH-AND-FACT-CHECK-RULES.md` exists precisely to stop unsourced travel prose reaching the runtime package. Both `app/src/main/assets/trip/trip.json` and `trip-package/sample/sample-trip.json` are back to what they were before Phase 4 and remain byte-identical to each other; the story is `"Narrativa de exemplo."` again. Reverting rather than retro-fitting sources: the content phase is not now, and a fixture that reads as placeholder cannot be mistaken for authored content.
- **D044 — The countdown belongs to the load, not to the arrival.** Screen 08 is a transition *into* playback, so it must not run when there is nothing to transition into. Setting it on arrival meant a traveller who tapped "Ouvir juntos" while the group was paused watched 3–2–1 count out and land on "Comece um audioguia para ouvir junto" — said about the very listen they were joining, and flatly contradicting what this repository claimed screen 08 was given to the joiner for. Of the two ways out named in review — do not start the count until there is something to enter, or give the wait a state of its own on screen 09 — the first is taken: the second needs copy the approved design does not carry, and one such item is already open. The count is now started by [loadIfInvited] at the moment the guide actually goes onto this player, which is the same instant as before for a group that is playing, and does not happen at all for one that is not. The invitation is kept while waiting, so the join happens when they start again. Two lines in the same method were also in the wrong order: the ask was spent before content was asked whether the guide is even packaged, so a guide missing from this build voided the invitation and no later snapshot could use it. Content is asked first now. Not reachable with the current package — found by reading, covered by a test.
- **D045 — A shared listen that has run past its own guide is over.** The group's `playback` node has no expiry: nothing writes a stop when a guide ends, and nothing writes one when everybody walks away, so it comes back the next day still saying "playing" with yesterday's anchor. The first time two devices ran together this was the first thing they hit — the traveller who tapped "Ouvir juntos" was treated as joining that dead listen rather than starting one, so no 3–2–1 and nothing published; the second phone, holding no guide, joined it and landed at 12:00 of a 12:00 guide, stopped, while the first played on at 02:58. Both screens read "Sincronizado". `isFinished` answers the question from data already in the payload — the anchor, the position, and the guide's own packaged length — and a listen that has run past its guide is treated as no listen at all, for joining, for divergence and for correction alike. D039 already refused to *resurrect* a finished guide on a phone that had it loaded; what was missing is that a phone with nothing loaded has no duration to compare against, so the same dead node could still be loaded onto it. One consequence had to be closed in the same breath: an ask that resolves to "nothing to join and nothing to propose" is now kept rather than spent, because the first answer the second phone gets is often exactly that, and spending it left the traveller watching the other phone count down without them. **Not fixed:** a *paused* node from an earlier session is still followed, and will pause a phone that arrives the next day. Telling it from a group that is genuinely paused needs either a session concept in the payload — a change, not a correction — or a timeout that would break a legitimately long pause. Recorded, not guessed at.
- **D046 — Corrections happen on the beat, not on the snapshot.** `GroupSyncState` deliberately maps `seenAt` away — the screens show a state, not a timestamp — so two consecutive snapshots of a group that is simply listening are *equal*, and the repository's `StateFlow` drops them. `onGroupState` therefore stopped being called as soon as two people settled, and every correction stopped with it. On the Galaxy S24 and the emulator: one traveller paused on screen 09 and was never resumed, the two drifted a full minute apart, and both screens went on reading "Sincronizado" with no note — the failure with no symptom, again, and one no single-phone pass could produce, because the earlier passes made the group's state change by hand in the Firebase console, which is exactly the case that still worked. Brief §5 says each device computes the expected position *periodically*; it now does, from the beat that D039 already runs, against the last snapshot the controller holds. Leaving and re-entering screen 09 was the only thing that used to fix it, which is what pointed at the cause. `applyCorrection` remains the single point of contact with the player.
- **D047 — Screen 09's transport acts on the shared listen.** Nothing published what the transport did: `startTogether` was the only writer and it always wrote `isPlaying = true`, so `SyncCorrection.Pause` and `SyncCorrection.Resume` — written, unit-tested, and recorded in D037 as how the group moves this phone — could only ever be produced by editing the database by hand. That is how "the group pausing this phone" came to be recorded as verified on hardware in Phase 4: the other side was the Firebase console, not a phone. With two devices the truth showed: one traveller paused, the other narrated on, they drifted a minute apart, and both screens said "Sincronizado". The approved design gives both phones the same full transport on screen 09 with no host and no client, and the product forbids inventing one, so pause, resume and ±15 there are things the group does. The payload is unchanged — the same five fields, anchored at now rather than three seconds out, because this corrects a listen that is already running rather than agreeing a new one. A phone that is not in the shared listen still publishes nothing (D042). *(Confirmed: "either traveller may pause the group" is the intended reading. The approved design gives both phones the same full transport on screen 09, with no host and no client, and the product forbids inventing one; there is nobody for the transport to belong to except the group. The question is closed, not carried.)*
- **D048 — "você" on screen 06 is the participant holding the phone.** The pill was labelled by list position — `index == 0` — with a comment above it correctly describing what it should have done. With one phone it read correctly by accident, because the traveller was the first participant in the package. On Érika's phone screen 06 said "Vinícius · você". The local participant id already reaches the route; it now reaches the state and the label compares ids, like screen 09's list already did.
- **D049 — Inside a shared listen, the system transport is a local control and the group wins.** Screen 09's transport publishes what it did (D047); the notification, the lock screen and a headset's own button do not. So during a shared listen a pause from any of those is undone by the next beat — the group is still playing, and D046 makes the correction actually happen — and the audio comes back within about five seconds. This was watched on the emulator, deliberately, as the proof that D046 works; what was not written down is what it means for the traveller, and that is the point of this entry. It is recorded as a decision rather than left as a side effect: while listening together, the shared listen is the thing being controlled, and the one surface that speaks for the group is the one the approved design draws for it. The consequence is that Phase 2's verified "headset media buttons pause and play both ways" holds *outside* a shared listen and not inside one, which both phase notes now say. The alternative — a pause from the system transport publishing too, exactly as screen 09's does — was flagged and is now *discarded, not pending*. A button pressed through a coat pocket is an accident, and an accident must not stop two people's narration; screen 09 is where one speaks for the group, and the approved design draws exactly one such surface. The system transport keeps controlling this phone alone, and the group puts it back.
- **D050 — The transport's state is what was asked for, not what the engine has confirmed.** `seekTo` always wrote the new position into `PlaybackState` itself and then told the engine; `play` and `pause` told the engine and waited for its listener. That left every reader depending on when the answer comes back, and D047 added a reader that acts in the very next statement: screen 09 publishes `isPlaying` to the group. It worked on both devices — a remote pause followed in 312 ms — because Media3's `MediaController` happens to report from inside the call, and nothing in this repository fixes that. Had it ever differed, pausing on screen 09 would have published `isPlaying = true` and asked the whole group to resume, with no error anywhere. `play` and `pause` now record the intent before asking the engine, the same shape `seekTo` has, which removes the ordering question for every reader rather than for this one. What the swap test cannot do is say *which* of two points is the wrong one - transposing either half of a transposed pair lands on the other half, by construction - so the subject depends on how much city there is: with three or more coordinates the wrong one is the one standing alone and is named, and with exactly two the finding names both and says there is no third point to break the tie. **Three absences are declared rather than papered over.** A transport endpoint is not checked: `transportEndpoint` declares no city, a leg's two ends are legitimately in different countries, and both ways to infer one are worse than nothing - `days[].cityIds` puts Amsterdam, Corfu, Sarande and Ksamil on one day, and a time zone is a political boundary that spans 60 degrees of longitude in China. A city with one packaged coordinate is not checked, because it has nothing to be compared with; the only cure would be a bounding box per `countryCode`, which is invented data inside a validator and is refused on the same grounds that kept the emergency telephone numbers out of the code. Both are printed by name, because an absent check said out loud is not a hole. **And a coincident pair is correct content, never a finding**: the real package's walk starts at its first stop, so `startLocation` repeats that stop's trigger, and in the sample the Latin Bridge story sits on the Latin Bridge attraction. A nearest neighbour at zero metres is the strongest agreement there is, and it has a test of its own so that nobody "fixes" it later. **Severity follows D095 exactly**: always an error, prototype/draft included. A point and its siblings are all already in the package and contradict each other, and no later step resolves it - unlike a document that declares `availableOffline` before its file has been produced.

- **D099 - The walk stop numbering is checked, and the two halves of it have different severities.** §27 asks for "bad walk ordering", and the target moved once the code was read: `WalkModeState.kt:105` does `sortedBy { it.order }`, so a walk numbered 1, 3, 2 does not break - it is **silently reordered** to 1, 2, 3 and runs correctly. What was missing is not reading, it is checking, and the two things that can go wrong are not the same kind of thing. **A duplicate is an error at every stage.** Two stops both numbered 2 leave which one the traveller walks first decided by `sortedBy` being stable - correct by accident, which is the worst way to be correct. Both stops are already in the package, they contradict each other, and no later step resolves it: this is D095's audio duration, one collection over. **A gap, or a first stop that is not 1, is a warning until production.** Stops numbered 1, 2, 4 sort into the right sequence and the walk runs; the missing 3 is content that has not arrived yet, and the promotion to production is exactly when it must have. This is D014's offline document, and the split is the same test applied twice: are these two facts already present and contradicting, or is this one fact still on its way? `stops[].storyId` is deliberately not checked here - `content_checks` already resolves it against the story registry, and a second copy of that rule is the defect D096 had just finished removing.
- **D100 - The sentence has to describe the condition the code tested, not the one the author had in mind.** D098's two-point finding printed "with no third coordinate in the city to say which of them belongs there". The condition the code actually tests is *both members of this pair are far from everything*, and three or more mutually distant points satisfy it just as two do. A city carrying Sarajevo, Paris and Sao Paulo produced two findings, each asserting there was no third coordinate, in a package that had three. The prose of D098 said the right thing - "with exactly two there is no cluster" - and the code generalised past it, which is the ordinary way a comment and a branch drift apart: the comment describes the case the author was thinking about and the branch accepts every case that reaches it. **The behaviour was correct and did not change**: with no cluster there is no way to choose a culprit, and refusing to choose is the right answer for two points and for ten. Only the stated reason was wrong. Two repairs were available - condition the old wording on `len(points) == 2`, or find one sentence true in every case that reaches the branch - and the second was taken, because a pair of wordings is a pair of things that can fall out of step again, which is the defect D096 had already removed once. The finding now says **"neither has a near neighbour in the city to anchor it"**, which is exactly what was tested, and the transposition diagnosis is unchanged behind it. The case has a test now; it had none, which is why nobody noticed the sentence was arithmetic-free.

- **D101 - The nearest neighbour asks whether a point has a friend; the diameter asks whether the city is a place.** D098 measured every coordinate against the nearest other coordinate in its own city, and that question has a blind spot with a name: **two coordinates wrong the same way become each other's friend**. Transposing two of the four packaged Sarajevo points leaves two tight groups 3,691 km apart, every single point with a neighbour 300 m away, and the check reports nothing at all - `findings=0`, `rc=0`, not one line. Transposing all four is the same silence. This matters more than it sounds, because it inverts which defect is guarded: **the transposition typed by hand is the rare one and it was caught; the transposition applied by a script or an agent to a group is the common one and it was not.** D098's own proof of failure only accused because the other three Sarajevo points happened to form a cluster - add a second transposed point to that same test and it goes green. So the city is now also measured against itself as a whole: **the distance between its two furthest points, against the same 100 km**, with no new constant, no new dependency and no external anchor. The headroom is the same two orders of magnitude on both sides - correct content spans 429 m in the sample and 296 m in the real package, a large sparse city would span ~25 km, and the blind case spans 3,691 km. **The diameter runs only where the nearest neighbour found nothing in that city**, which keeps one defect to one finding: a single wrong point stretches the diameter too, and where the nearest neighbour can name the culprit its message is the better one. That has a cost, and it is named rather than discovered: a city carrying *both* a lone wrong point and a transposed group reports only the lone point, and the group surfaces on the next run once the first is fixed. The message names the two extremes and refuses to pick, on D100's reasoning - with the city split into two coherent groups nothing in the package says which group is the city - and adds the transposition sentence when swapping either end resolves it. One limit is asserted in a test rather than left implicit: **a city moved wholesale is internally consistent and cannot be caught here**, because it is one place, and the wrong one.

- **D102 - The guide names the place, the story carries the sentence, and now something checks it.** Screens that resolve a story's audio show `story?.title ?: guide?.title` - a fallback, one or the other. **The player is not a fallback: it shows both at once.** `WalkModeController.kt:231` passes `subtitle = story.title` into `audioGuideRequest`, `AudioGuideRequest.kt:49` sets `title = guide.title`, `AppNavigation.kt:462-463` hands the pair to the compact player as `title` and `compactSubtitle()`, `PlaybackState.kt:56` returns the raw subtitle when there are no chapters, and `Media3AudioEngine.kt:70-73` puts them in the media session as `setTitle` / `setArtist` / `setSubtitle`. The three Sarajevo guides shipped that way: `title` identical to the story's, promoted into the APK, and **no tool caught it** - it was found by review reading the player chain. *(Corrected on 2026-09-05, when the guard ran for the first time: this paragraph first said the origin was an instruction that told the author to use the same title and asserted that no screen showed both. - **D103 — The geofence is an alarm clock, not a judge, and the floor is 120 m.** Passive story discovery had one honest way to fail and one dishonest one, and the dishonest one is the interesting half. The three real triggers declare `radiusMeters: 80`. Registering an Android geofence at 80 m is the honest failure: the platform promises nothing at that scale, latency grows as the radius shrinks, and the result is a circle that *sometimes* does not ring — which is worse than no circle, because nobody can tell the difference between "no story here" and "the story failed to fire". The dishonest fix is to raise the content's radius to something the platform can watch, and it would have worked in the emulator and been wrong in Baščaršija: the three Sarajevo triggers are 260–380 m apart, so an 80 m circle widened to 120 m starts announcing the Sebilj from the far side of Ferhadija, and "você está aqui" becomes a lie in the one place this app has to be trustworthy. **So the two numbers are separated instead of reconciled.** `GEOFENCE_FLOOR_RADIUS_METERS = 120f` is a *registration* number and never reaches a decision: the content's 80 m plus the ~40 m a fused fix carries in a dense old town, which is the smallest ring that can be trusted to ring. When it rings, the position delivered with the wake-up goes through `decideStoryTrigger` at the trigger's own 80 m. **`Nothing` is the expected answer there, not an error** — the outer circle exists precisely so that it will sometimes be too early. Which is the whole point: nothing outside `decideStoryTrigger` compares a distance with a radius. D096's defect is a rule written twice, and widening the radius is the shape that would have reintroduced it *while passing every test*, so the floor lives alone as a `const` with `registrationRadiusMeters` beside it, commented the way `COORDINATE_CLUSTER_LIMIT_METERS` is in the validator: a tuning number that is not a rule must not be mistaken for one. One consequence is named rather than discovered — crossing the outer rim at 100 m and then walking to the plaque produces no second ENTER — so `GEOFENCE_TRANSITION_DWELL` is registered alongside ENTER with a one-minute loiter: a second ring of the same alarm, not a second decision. `ACCESS_BACKGROUND_LOCATION` returns to the manifest on exactly the terms D033 removed it under: it is used now, by this, and by nothing else. Play Services geofencing is also why any of this may exist outside a walk — the system watches the circles with the location it is already spending, so `LocationSource`'s line that high-accuracy GPS must not run outside Walk Mode is untouched.

- **D104 — A refused background permission is answered once, on screen 19, and costs one thing only.** From Android 11 the system shows no dialog for `ACCESS_BACKGROUND_LOCATION` at all: requesting it returns a refusal the traveller never saw, and the only real path is Android's own settings page.
