# Lightweight Decisions

Record only decisions that materially affect maintainability or visible behavior.

- **D001 — One app module for V1.**
- **D002 — Firebase deferred from bootstrap.** Group sync already has an interface boundary.
- **D003 — Stable API 36 baseline.**
- **D004 — Runtime state never mutates packaged trip content.**
- **D005 — Real font binaries are added later; design typography remains locked.**
- **D006 — Lifecycle pinned to 2.10.0.** 2.11.0 requires compileSdk 37 / AGP 9.1.0 and cannot build on the API 36 baseline. See `docs/technical/DEPENDENCY-BASELINE.md`.
- **D007 — JDK 17 toolchain is auto-provisioned.** Foojay resolver in `settings.gradle.kts` keeps the pinned JDK 17 baseline working on machines that only have Android Studio's JDK 21.
- **D008 — The packaged trip is the sample Day 9 dataset.** `app/src/main/assets/trip/trip.json` is a copy of `trip-package/sample/sample-trip.json`; the minimal starter could not exercise screens 02 and 05. The approved `02 -> 05` flow opens **Baščaršija**, so that attraction, its audioguide and its rain Plan B were transcribed from the approved prototype into the sample package. Latin Bridge stays in the package as a second attraction that does *not* start the walk.
- **D009 — Trip length comes from the trip date window,** not from how many days are packaged, so "Dia 9 de 21" stays true while content for the other days is produced. The sample `endDate` was `2026-10-02`, a 20-day window that contradicted the approved "21 dias"; it is now `2026-10-03`. `validate_trip.py` checks every `dayNumber` against the window so this class of drift cannot return.
- **D010 — No image-loading library.** Packaged photography is decoded straight from assets; a missing binary falls back to the approved striped placeholder.
- **D011 — A walk names its starting attraction explicitly.** `walk.startAttractionId` was added to `trip.schema.json`. Sharing a `cityId` is not an association: every attraction in Sarajevo would otherwise claim the walk departs from it, and screen 05 would offer "Iniciar passeio" from the wrong place.
- **D012 — Duplicate critical items are merged, never de-duplicated.** The same item is routinely declared twice — curated on the day and in full on the transport that owns it. `distinctBy(id)` silently dropped "Ver ponto de embarque"; `CriticalItem.mergedWith` now unions the action links and keeps the first non-null of every field.
- **D013 — "Offline" is earned, not declared.** A document is only badged offline when `availableOffline` is true *and* `AssetResolver` finds the packaged file. Claiming offline access over a missing PDF is the one failure that only surfaces at a bus station.
- **D014 — `validate_trip.py` checks what JSON Schema cannot:** unresolved references, duplicate IDs, `dayNumber` against the trip window, and documents that promise offline access without a packaged file. Findings are warnings while `contentStatus` is prototype/draft and errors once it is `production`.
- **D015 — Playback is application-scoped.** `PlaybackController` lives on `AppContainer` and the player itself lives in a `MediaSessionService`. A screen-scoped player would stop the audioguide the moment the traveller navigates away or the phone rotates, which is exactly when the phone goes into a pocket.
- **D016 — A narrow `AudioEngine` seam sits between the controller and Media3.** It keeps ExoPlayer out of ViewModels and Composables, and it is what makes playback coordination testable without a device. It is deliberately limited to the operations the app performs.
- **D017 — Audio plays from `asset:///` URIs resolved by `AssetResolver`.** Bundled audio is read straight out of the APK and is never streamed; a guide whose file is absent reports `AudioNotPackaged` instead of failing in the decoder.
- **D018 — No notification permission prompt for the audioguide.** *(Corrected: an earlier revision requested POST_NOTIFICATIONS at the first tap.)* A `MediaSessionService` notification is exempt from the Android 13+ runtime permission, so the prompt bought nothing and interrupted the traveller before a single second of audio had played. The manifest declaration stays for the operational notifications of Phase 7, which do need it.
- **D019 — A documented prototype audio placeholder is packaged.** `trip/audio/attractions/bascarsija.prototype.wav` is synthesised by `tools/make_prototype_audio.py` (CC0, no third-party material: a short sine marker at each chapter start, silence in between) so the real playback flow can be exercised on a device. It runs the approved 720 s, so `ag.bascarsija` keeps `durationSeconds: 720` and screen 05 reads "Ouvir audioguia · 12 min" while the stated duration still matches the file on the device. It is labelled in the asset description and in `trip/audio/README.md`; only its chapter titles describe the placeholder rather than real narration.
- **D020 — Screen 05 keeps its approved action; playback surfaces in the compact player.** Screen 05 specifies one action ("Ouvir audioguia · N min") and screen 09 is the shared-player screen, so neither is reinterpreted. The design system's `TcAudioPlayer` compact variant — "the persistent bottom player … stays available while navigating" — lives in the shell above the bottom navigation. The full 52/68/52 transport is implemented in the same component and waits for screens 07/09.
- **D021 — An unplayable guide never disturbs playback.** A guide whose audio is not packaged is not offered at all (availability is known from content), and requesting one is a no-op: audio that is already playing keeps playing and the state keeps describing it. The UI and the engine can no longer disagree.
- **D022 — A finished guide replays from the start.** After `Ended`, both a fresh request and the play toggle seek to 0 and play, instead of resuming at the end where nothing would happen.
- **D023 — "Not playing" never overwrites a terminal state.** In Media3 `isPlaying = false` means paused, buffering, ended, failed, stopped *or* suppressed, and it can arrive before or after the state change that explains it. `Ended` and `Failed` therefore win over a bare pause signal, in either order, and a guide that ended is not given a resume point by the pause that follows it.
- **D024 — A lost connection drops its queue.** If `buildAsync` fails the pending commands are cleared; if the session disconnects, the player listener is removed and the controller is detached. Replaying a stale `prepare`/`play` after a later retry would resume the wrong guide; the next command reconnects from scratch instead.
- **D025 — Seek and chapter selection are deferred to their approved surfaces.** Both are implemented and tested on `PlaybackController`, but the canonical screens put the −15/+15 transport on 07/09 and the chapter list on 04. Exposing them anywhere else would add a screen, which needs design review (`DESIGN-HANDOFF-v2.md` §10). **Approved decision: option (a)** — no solo player is created, and neither ±15 nor chapter selection is added to the compact player. Phase 2 ships play/pause as its reachable behaviour; the capabilities wait for Phases 3/4/6.
